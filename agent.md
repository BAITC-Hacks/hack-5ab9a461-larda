# Правила работы над Larda

## Перед изменениями

1. Прочитать `contextn.md` и `progress.md`.
2. Проверить `git status --short` и текущую ветку. Сохранять чужие и незавершённые изменения; не откатывать их ради чистого дерева.
3. Уточнить по коду, что уже реализовано. Переписка и планы не являются доказательством работающей функции.
4. Обновлять `progress.md` после завершённого этапа: что изменилось, чем проверено, что осталось.

## Границы модулей

Целевая структура пересборки:

```text
src/app/        маршруты, оболочка, провайдер состояния
src/domain/     типы и чистые бизнес-правила
src/data/       интерфейс репозитория и локальная реализация
src/features/   бизнес-кабинет, задачи, каталог, отклики
src/shared/     общие UI-компоненты и анимации
```

- Страницы отвечают за отображение и пользовательский сценарий. Изменение данных проходит через предоставленный приложением репозиторий/провайдер.
- Бизнес-правила не зависят от React, DOM, маршрутов и `sessionStorage`.
- Доступ к хранилищу и будущему API сосредоточен в слое данных. Не читать браузерное хранилище из отдельных страниц.
- Общие UI-компоненты не импортируют страницы или feature-модули. Не создавать циклические зависимости между feature-модулями.
- Новую возможность добавлять отдельным feature-модулем; подключать маршрут в `src/app`. Общие сущности и правила добавлять в `src/domain` только при реальном совместном использовании.
- Изменение транспорта или формы ответа backend закрывать адаптером данных. Не переписывать UI под названия SQL-колонок.
- Перед добавлением нового компонента проверить существующие кнопки, статусы, подсказки и прогресс. Цвета и длительности брать из общих CSS-токенов.

## Продуктовые правила

- Главная аудитория — владелец/менеджер МСБ. Понятные русские названия, крупные доступные кнопки, одно главное действие на экран.
- Основные термины: «Создать задачу», «Готовность задачи», «Отклики команд», «Выбрать команду», «Отклонить».
- Анимации объясняют результат действия и переход; учитывать `prefers-reduced-motion`, клавиатуру и видимый фокус.
- Не выдавать локальную имитацию помощника за подключённый AI. Не подставлять вымышленные ответы за введённый пользователем текст.
- Backend сейчас отсутствует. Не придумывать endpoints, авторизацию или подтверждённый API-контракт.
- ERD пользователя — источник структуры будущего backend. Не возвращать модель организаций из раннего обсуждения: задача принадлежит `USERS` через `owner_id`.
- EXP, достижения и этапы работ присутствуют в ERD, но не входят в текущую реализацию интерфейса без отдельного запроса.

## Проверка и передача

- Проверить `npm run build`.
- Когда добавлен E2E-набор, выполнить `npm run test:e2e`; до появления script не писать, что команда работает.
- Пройти создание задачи → уточнения → публикацию → отклик → ручной выбор команды; проверить прямые ссылки, refresh и браузерные назад/вперёд.
- Проверить reduced motion и макет на ширине 1280 px. Не отмечать визуальную проверку выполненной по одному успешному build.
- Не занимать порт 5173 оставленным тестовым сервером: пользователь запускает dev-сервер самостоятельно. Для временной проверки использовать отдельный порт и завершать только свой процесс.
- В `progress.md` указывать фактический результат проверок и ограничения. В `contextn.md` фиксировать устойчивые решения, а не пошаговый журнал действий.
