# Larda — задания бизнеса для студенческих команд

Бэкенд на Go, Gin, GORM и PostgreSQL. Бизнес превращает описание проблемы в карточку с помощью OpenAI, публикует её, выбирает команды и принимает результаты этапов. Студенты получают EXP и достижения. REST-контракт: [docs/openapi.yaml](docs/openapi.yaml); требования: [Task.md](Task.md), модель данных: [ERD.md](ERD.md).

## Запуск

Нужен Docker с Docker Compose v2. Команды для PowerShell из корня проекта:

```powershell
Copy-Item .env.example .env
# Откройте .env: задайте OPENAI_API_KEY либо установите AI_MODE=fallback.
docker compose up --build -d --wait
Invoke-RestMethod http://localhost:8080/healthz
```

`AI_MODE=openai` вызывает OpenAI с ключом из `.env`. По умолчанию используется настраиваемая модель `OPENAI_MODEL=gpt-4o-mini`. Промпты и строгие JSON-схемы находятся в `internal/adapters/ai/`. Адаптер использует [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Для демонстрации без сетевых запросов к модели и расхода кредитов явно укажите `AI_MODE=fallback`. Этот режим проверяет заполненность полей и возвращает `source: "fallback"`; он не оценивает смысл текста. При ошибке OpenAI сервер сохраняет `failed` и не переключается в fallback автоматически. После изменения `.env` выполните `docker compose up -d --build --wait`.

API: `http://localhost:8080/api/v1`. `/livez` проверяет процесс, `/healthz` и `/readyz` — доступность БД. Логи: `docker compose logs -f api`. Остановка с сохранением данных: `docker compose down`. Имя проекта Compose — `larda`, том PostgreSQL — `larda_postgres_data`. Тома, созданные под прежним именем проекта, сохраняются отдельно и автоматически не переносятся.

`.env` исключён из Git; настоящий ключ нельзя коммитить. Основные настройки перечислены в [.env.example](.env.example): `AI_MODE`, `OPENAI_API_KEY`, `OPENAI_MODEL`, `AI_TIMEOUT`, `DATABASE_URL`, `SEED_DEMO`, `CORS_ORIGINS`, порты API и PostgreSQL. CORS разрешает только перечисленные точные origin.

Для локального Go-запуска нужен Go 1.24+:

```powershell
docker compose up -d db --wait
go run ./cmd/api
```

Приложение читает `.env`; локальный `DATABASE_URL` должен указывать на доступный порт PostgreSQL. Контейнер API получает адрес БД из Compose.

## Демо и роли

Регистрации, паролей и JWT нет. Заголовок `X-Demo-User-ID` выбирает демопользователя. Это переключатель личности для хакатона, а не настоящая авторизация: клиент может указать любой существующий ID.

На новой БД с `SEED_DEMO=true` создаются:

| ID | Пользователь | Возможности |
| --- | --- | --- |
| 1 | Бизнес | Свои карточки, выбор команд, утверждение и приёмка этапов |
| 2 | Студент-капитан | Состав команды, отклики, предложения этапов, сдача результатов |
| 3 | Обычный студент | Просмотр команды и её откликов, собственные навыки и профиль |

Капитанство — роль в команде; оба студента имеют пользовательскую роль `student`. Эти же два студента входят в пять демонстрационных команд. Создаются пять опубликованных задач с ID 1–5, пять черновиков с ID 6–10 и примеры откликов. Публичные оценки примеров помечены `source: "demo_seed"`.

Начальное заполнение не вызывает платный API. Черновики получают `ai_status: "failed"` с пояснением о ручном запуске: бизнес может вызвать `POST /api/v1/tasks/6/ai/retry`. Повторный запуск сервера не дублирует демоданные; если пользователи уже существуют, наполнение пропускается. В существующей БД ID следует получать через API.

```powershell
Invoke-RestMethod http://localhost:8080/api/v1/users
Invoke-RestMethod http://localhost:8080/api/v1/tasks
Invoke-RestMethod http://localhost:8080/api/v1/tasks/mine -Headers @{'X-Demo-User-ID'='1'}
```

Полный демонстрационный сценарий создаёт новую задачу, показывает рост оценки и сохранность публичной версии, затем проходит отклик, этап, приёмку и начисление EXP:

```powershell
# Для бесплатного прогона API должен быть запущен с AI_MODE=fallback.
powershell -NoProfile -ExecutionPolicy Bypass -File ./scripts/demo.ps1
# Другой адрес:
./scripts/demo.ps1 -BaseUrl http://localhost:8080
```

Скрипт использует обычные HTTP-запросы к запущенному API. При `AI_MODE=openai` его операции запускают обращения к модели. Каждый прогон оставляет новую задачу и результаты в БД.

## Карточка и AI

1. Бизнес отправляет `POST /api/v1/tasks` с `raw_description`. Сервер атомарно сохраняет задачу и AI-задание в PostgreSQL, отвечает `202`, затем фоновый worker вызывает модель.
2. `GET /tasks/{id}` возвращает владельцу `ai_status`; `GET /tasks/{id}/ai-jobs` — историю операций. После успеха `GET /tasks/{id}/questions` возвращает 3–7 вопросов. Поддерживается один раунд уточнений.
3. `POST /tasks/{id}/answers` принимает текущую `revision` и ответы на все вопросы. Модель формирует редактируемую карточку и оценивает её.
4. `PATCH /tasks/{id}` принимает `revision` и изменённые поля. Каждое сохранение увеличивает версию и запускает новую оценку; устаревшая версия получает `409`. Предварительная оценка доступна владельцу в `draft_evaluation`.
5. `POST /tasks/{id}/confirm` с актуальной `revision` подтверждает успешно оценённый черновик. `POST /tasks/{id}/publish` публикует карточку. Низкий балл не запрещает публикацию или отклики.
6. Изменения опубликованной задачи остаются приватными до следующего подтверждения. Подтверждение атомарно заменяет публичные поля и рейтинг. Другие пользователи не получают исходное описание, черновик, вопросы или AI-задания.

Модель определяет баллы по содержанию, причины и недостающие сведения. Сервер проверяет семь критериев, допустимые диапазоны и сумму от 0 до 100; в режиме OpenAI сервер не заменяет оценку модели собственной эвристикой.

| Критерий | Максимум |
| --- | ---: |
| Контекст и потребность (`context_need`) | 20 |
| Данные (`data`) | 20 |
| Ожидаемый результат (`result`) | 15 |
| Критерии успеха (`success_criteria`) | 15 |
| Ограничения (`constraints`) | 10 |
| Целевые пользователи (`users`) | 10 |
| Коммуникация (`communication`) | 10 |

Категории готовности: `draft` — 0–39, `working` — 40–69, `ready` — 70–89, `priority` — 90–100. Категория вычисляется из балла и не зависит от статуса публикации.

AI работает вне транзакции БД. Очередь хранится в таблице `ai_jobs`; worker забирает задания с блокировкой и арендой на пять минут, вызов ограничен двумя минутами и настройкой `AI_TIMEOUT`. Версия карточки и токен аренды защищают от записи устаревшего ответа. После обычной ошибки нужен явный `POST /tasks/{id}/ai/retry`; автоматических платных повторов нет. После аварийного завершения процесса истёкшая аренда позволяет восстановить задание, поэтому незавершённый внешний вызов в таком случае может повториться.

## Команды, этапы и EXP

Каталог поддерживает `topic`, `industry`, `readiness`, `tag_ids`, `limit` и `offset`. Теги команды собираются из навыков участников. Публично доступны задачи, команды, пользователи и достижения; изменения и приватные чтения требуют заголовок демопользователя.

Отклик содержит идею, план, срок и необязательную ссылку на прототип. Только капитан подаёт его от команды. Бизнес принимает (`accepted`) или отклоняет (`rejected`) отклик; для задачи можно выбрать несколько команд, прогресс каждой учитывается отдельно.

Для выбранной команды этап предлагает капитан или владелец задачи. Предложение капитана требует утверждения бизнеса; созданный бизнесом этап утверждается сразу. Капитан сдаёт результат ссылкой `http(s)`, бизнес принимает его либо возвращает на доработку. Завершение работы команды требует хотя бы одного утверждённого этапа и выполнения всех утверждённых этапов; неподтверждённые предложения не блокируют завершение. Завершение задачи разрешено, когда работы выбранных команд завершены или отменены и есть завершённая команда.

EXP за этап делится между участниками команды на момент завершения этапа, остаток распределяется по возрастанию ID. При завершении задачи каждая отдельная завершившая работу команда получает командную награду один раз, её делят текущие участники; бизнес получает свою награду. Достижения также добавляют EXP.

Капитан может менять состав и передавать капитанство во время работы. Изменения состава и выплаты используют одну блокировку команды, поэтому участники для распределения определяются согласованно. Транзакции и уникальные записи журнала, включая записи с нулевой долей, предотвращают повторные начисления. Повторный запрос завершения не выдаёт новую награду и не доплачивает участникам, добавленным после первой выплаты.

## Архитектура и хранение

Гексагональная архитектура отделяет сценарии приложения от Gin, GORM и OpenAI:

```text
cmd/api                    сборка зависимостей, HTTP-сервер, worker, остановка
internal/domain            сущности, ошибки, правила оценки и распределения EXP
internal/ports             интерфейсы Repository / Store и AI
internal/application       сценарии, права, транзакции, жизненный цикл карточки
internal/adapters/httpapi  Gin, REST, JSON, CORS, демопользователь
internal/adapters/postgres GORM, PostgreSQL, миграции, демоданные
internal/adapters/ai       OpenAI, промпты, JSON-схемы, явный fallback
internal/config            конфигурация и .env
migrations                 версионированные SQL-миграции up/down
docs/openapi.yaml           контракт REST API
```

При старте применяются встроенные SQL-миграции под advisory lock; таблица `schema_migrations` хранит применённые версии. `AutoMigrate` не используется. Если исходная схема из первоначального SQL уже существует, первая миграция принимается как применённая, затем добавляются новые изменения. Это рассчитано на совместимую исходную схему проекта. `down.sql` предназначены для явного ручного отката и автоматически не выполняются.

API ограничивает JSON-тело 1 MiB, отклоняет неизвестные поля и возвращает ошибки в формате `{"error":{"code":"...","message":"..."}}`. Основные коды HTTP: `400` — входные данные, `403` — права, `404` — отсутствующий ресурс, `409` — конфликт состояния/версии. Детали БД и секреты не выдаются клиенту.

## Проверка

```powershell
go test ./...
go vet ./...
```

Без `TEST_DATABASE_URL` тесты PostgreSQL пропускаются. Для полного прогона поднимите отдельную тестовую БД:

```powershell
docker compose -f compose.test.yaml up -d --wait
$env:TEST_DATABASE_URL = 'postgres://larda:larda@localhost:55432/larda_test?sslmode=disable'
go test ./...
go vet ./...
Remove-Item Env:TEST_DATABASE_URL
docker compose -f compose.test.yaml down
```

Интеграционные тесты создают отдельную случайную схему на тест и удаляют только её. Проверяются полный цикл карточки, публичный снимок, ошибки и ручные повторы AI, устаревшие ответы, права капитана/бизнеса, этапы и однократное начисление EXP и достижений. HTTP-тесты проверяют приватность, валидацию JSON, лимит тела, CORS и безопасные ошибки.
