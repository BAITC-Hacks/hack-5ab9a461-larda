# Геймификация Larda: правила MVP

## Общее событие, разные представления

Принятие результата бизнесом фиксирует review с автором и временем. Бизнес видит принятый результат и долю завершённых этапов. Студент видит XP за подтверждённый вклад, доказательства навыков и, после завершения проекта, профессиональный опыт.

Владелец — пользователь `ownerId`; отдельной организации нет. Все ID строковые. Модель frontend расширяет ERD для локального сценария и не задаёт утверждённый HTTP-контракт.

## Выполнение

Выбор одной команды не запускает работу. Бизнес отдельно вводит критерии и даты трёх этапов (анализ / прототип / итог), затем фиксирует brief, навыки и участников. Даты должны быть календарными, не ранее дня старта и идти по порядку; несколько этапов могут иметь одну дату. После старта нельзя изменить согласованную задачу.

Капитан отправляет следующий непринятый этап: описание, HTTP(S) ссылка, участники, их вклад и выбранные навыки проекта. Нельзя отправить второй результат до решения по первому, чужого участника или навык вне проекта. Список навыков может быть пустым; это не создаёт доказательства мастерства.

Для запроса доработки нужна обратная связь. Для принятия нужен хотя бы один подтверждённый участник из отправленной версии. Подтверждая участника, бизнес подтверждает указанное описание и навыки. Изменить описание/навыки можно через доработку, а не после принятия. Все версии, решения и ссылки сохраняются.

Принятые этапы неизменяемы. Повтор решения для уже рассмотренной версии — идемпотентный no-op. Финальное принятие завершает task, proposal и project. Отмена, переоткрытие и отзыв наград в MVP отсутствуют.

## XP, уровни и достижения

Ledger — источник XP; профиль не хранит независимый изменяемый баланс. Ключ награды этапа включает этап и пользователя, ключ достижения — пользователя и достижение. Принятие, изменение состояний и бонусы сохраняются единым snapshot до уведомления UI.

Награды этапов: 200 / 300 / 300 XP каждому подтверждённому участнику. Ранг: E (0 XP, 0 проектов), D (1000, 1), C (2500, 2), B (5000, 3), A (10000, 5), S (20000, 10). Уровень L: порог `50*L*(L-1)`, начальный уровень 1. Максимальный ранг — S, уровни продолжаются.

Проект входит в опыт пользователя только после полного завершения и хотя бы одного принятого личного вклада. Навыки связываются с подтверждёнными вкладами даже до завершения проекта. Роль в портфолио берётся из зафиксированного состава.

Три достижения: «Первая миссия» (1 проект, +100), «Решение найдено» (5 проектов, +300), «Проверено бизнесом» (3 различных ownerId завершённых проектов, +200). Повторный бонус невозможен. Проверка аккаунта не является проверкой компании.

Новые транзакции показываются в доступном блоке прогресса, пока студент не нажмёт «Продолжить». Подтверждение просмотра хранится отдельно от начисления; refresh не создаёт новую награду. Read-only пример профиля предоставляется отдельным методом repository и не сливается с рабочими данными.

## Бизнес-контроль

Очередь: результаты на проверке → просроченные этапы → ожидающие решения отклики → подготовка задач и старта → активные → завершённые проекты. Внутри группы сначала ранний срок. Принятый этап не становится просроченным. Задача может появиться и в очереди проекта, и в оставшихся ручных решениях по другим откликам.

Готовность постановки — отдельная сумма семи категорий. Детали арифметики приведены в README. Пустые поля получают 0, пробелы не считаются заполнением. Рекомендации — три отсутствующих поля с наибольшим возможным приростом. Сохранение показывает реальную разность, включая отрицательную. Рейтинг влияет на сортировку каталога; обещаний автоматического подбора, финансового эффекта или приоритетного сервиса нет.

## Локальная AI-заглушка

Внешние запросы не отправляются. Интерфейс явно сообщает о заранее подготовленных вопросах.

Промпт (также экспортируется в доменном модуле assistant):

> Определи недостающие сведения карточки. Верни JSON {questions:[{fieldKey,question}]} с минимум тремя вопросами. Не добавляй фактов или ответов. Используй только поля из входной схемы.

Вход:

```json
{
  "taskId": "demo",
  "card": {
    "title": "Учёт заявок",
    "context": "Заявки переносят вручную",
    "need": "",
    "targetUsers": "",
    "contact": "",
    "expectedResult": "",
    "successCriteria": "",
    "availableData": "",
    "constraints": "",
    "interactionFormat": "",
    "feedbackProcess": ""
  }
}
```

Выход:

```json
{
  "questions": [
    { "fieldKey": "expectedResult", "question": "Что должна сделать команда?" },
    {
      "fieldKey": "successCriteria",
      "question": "Как вы поймёте, что задача решена?"
    },
    {
      "fieldKey": "availableData",
      "question": "Какие данные вы можете предоставить?"
    }
  ]
}
```

Валидатор допускает 3–9 вопросов с непустым текстом, уникальными известными ключами. Некорректный ответ заменяется тремя детерминированными вопросами. Результат помощника содержит только вопросы; факты и баллы он менять не может. Ввод, выход, fallback и отсутствие вымышленных данных покрыты тестами. Это демонстрация интеграционной границы, не работающая AI-модель.

## Хранение и будущий backend

Версия 2 добавляет agreements/projects, milestones, submissions, reviews, XP ledger, achievement unlocks и квитанции просмотра наград. Миграция v1 дополняет отсутствующие поля пустыми строками, пересчитывает готовность и оставляет принятые предложения до ручного старта. v1 не удаляется; v2 сохраняется при первом успешном действии. Нечитаемый snapshot не изменяется загрузкой; интерфейс начинает с синтетического набора.

Для чистого демо удалите оба ключа `larda.workspace.v1` и `larda.workspace.v2` в DevTools и обновите страницу. Это удаляет локальные демо-данные вкладки.

Будущий backend обязан повторить проверки владельца, членства, переходов, idempotency и атомарности в серверной транзакции. Текущий переключатель роли не является аутентификацией.
