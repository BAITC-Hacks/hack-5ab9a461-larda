## Быстрый запуск серверного сценария

1. Запустить frontend: `npm run dev`; открыть `/connected` на его адресе.
2. Ввести URL backend (корень или с `/api/v1`), нажать «Подключиться».
3. Выбрать бизнес-профиль, описать проблему, дождаться AI, ответить на все вопросы. Проверить/исправить карточку, подтвердить факты, опубликовать.
4. Выбрать студента — капитана команды; открыть задачу и отправить заявку. Участник без роли captain может только читать.
5. Вернуться в бизнес-профиль, открыть задачу, выбрать команду, добавить согласованный этап.
6. Капитан отправляет ссылку; бизнес возвращает на доработку или принимает. Затем явно завершает работу команды и всю задачу.
7. Переключиться на студента: XP и история загрузятся с backend.

Backend должен разрешать точный origin frontend в `CORS_ORIGINS`. На HTTPS-странице нужен HTTPS backend. Ключ модели хранится только на backend; `AI_MODE=fallback` не вызывает внешнюю модель, `AI_MODE=openai` требует настройки сервером. При сетевой ошибке сначала «Обновить данные»: мутация могла сохраниться. Автоматических повторных отправок нет.

Ограничения этого кабинета: нет пагинации после первых 100 задач, редактирования команд, достижений/рангов локального MVP и сохранения выбранного экрана после refresh. Команды загружаются при подключении — после изменения членства переподключитесь. Локальные данные и серверные записи не смешиваются.

## Как запустить и проверить

Нужен сам backend-репозиторий или адрес запущенного API. Следующие команды выполняются **в корне backend**, не в текущем frontend:

```bash
# Только если .env отсутствует:
cp -n .env.example .env
# В .env установите AI_MODE=fallback для бесплатного локального сценария.
docker compose up --build -d --wait
curl http://localhost:8080/healthz
curl http://localhost:8080/api/v1/users
```

Если .env уже есть, редактировать его, не перезаписывать. Ключ внешнего AI хранится только на сервере. По документации fallback не делает внешних AI-запросов; режим openai не переключается автоматически в fallback после ошибки.

В Postman импортировать оба JSON, выбрать environment и `01 Full workflow`, установить задержку Runner 1000 мс. `base_url` Postman — `http://localhost:8080`, пути коллекции уже включают `/api/v1`. Обычный Send не выполняет циклы Runner. Полный workflow изменяет БД: создаёт ресурсы, обновляет навыки и начисляет EXP; запускать на тестовой базе. Этот разбор коллекцию не запускал.

Frontend API base — `http://localhost:8080/api/v1`. Разрешены origins `http://localhost:5173` и `http://localhost:3000`; для `http://127.0.0.1:4175` тестового браузера нужно явно добавить origin в CORS_ORIGINS. localhost и 127.0.0.1 различаются.

## Что можно подключить существующим API

Каталог и фильтры; пользователи и команды; создание/редактирование задачи; AI-вопросы и оценка; подтверждение и публикация; предложения команд; ручной выбор; создание/утверждение этапов; отправка URL; принятие/отклонение; явное завершение/отмена; серверные EXP и достижения.

Нет отдельного GET proposal или milestone. Бизнес читает `GET /tasks/{id}/proposals`, студент — `GET /teams/{id}/proposals`; milestones вложены в proposals. Профиль `GET /users/{id}` содержит `user`, `tags`, `achievements`, `exp_history`.

## Расхождения с реализованным локальным MVP

| Возможность             | Локальный MVP                                    | Присланный backend                                       | Следствие                                                                    |
| ----------------------- | ------------------------------------------------ | -------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Получатели XP           | Подтверждённые участники, полный XP каждому      | Общая награда делится между текущими участниками         | Нельзя сохранить индивидуальную верификацию одним адаптером                  |
| Состав команды          | Зафиксирован при старте                          | Берётся на момент выплаты                                | Смена состава меняет получателей                                             |
| Старт                   | Отдельное подтверждение после выбора команды     | Принятие отклика сразу включает in_progress              | Нужны изменения сценария или отдельный серверный старт                       |
| Команды и отклики       | Одна выбранная команда, один отклик команды      | Несколько принятых команд и повторные отклики разрешены  | UI/селекторы не должны предполагать уникальность                             |
| Этапы                   | Три последовательных этапа с критериями и датами | Произвольные milestones с title/description/exp_reward   | Три этапа можно создавать шаблоном, но нет атомарного старта и поля срока    |
| Передача работы         | Summary, URL, contributors, skills, версии       | Только result_url                                        | Нет контракта хранения вклада, навыков и истории версий                      |
| Решение бизнеса         | Решение, комментарий и подтверждённые участники  | Только accepted:boolean; feedback не принимается         | Нельзя сохранять объяснение доработки или индивидуальное подтверждение       |
| Завершение              | Автоматически после третьего принятия            | Отдельно complete proposal, затем complete task          | Последнее принятие не означает завершение или финальную выплату              |
| Награды/достижения      | Локальные фиксированные правила                  | Серверный каталог и серверные транзакции, включая бизнес | В API-режиме нельзя начислять локальный XP поверх серверного                 |
| Навыки                  | Доказательства принятого вклада                  | Редактируемые пользователем tags                         | Самостоятельно выбранный тег нельзя показывать как подтверждённое мастерство |
| Вопросы                 | Три предложенных, ответы сохраняются отдельно    | 3–7, один запрос со всеми актуальными answers и revision | Нужен буфер ответов и массовая отправка, реальные question_id                |
| Оценка и редактирование | Локальный немедленный пересчёт                   | Асинхронный job, draft_evaluation и revision             | Требуются loading/error/retry, polling и раздельные private/public snapshots |
| ID                      | Строки, новые UUID                               | Числовые JSON ID                                         | Нужен DTO mapper, локальные UUID нельзя отправлять в API                     |

Источники ключевых расхождений: `for_frontend.md` разделы Proposals, Milestones, EXP; `json.md` разделы Create milestone, Submit milestone result, Review milestone result, Profile.

## Предлагаемый порядок подключения (ещё не реализован)

1. Получить адрес/исходники backend и OpenAPI; проверить health, CORS, список пользователей и реальную форму ответов.
2. Добавить HTTP-клиент и отдельный API repository. Точка подключения — композиция приложения; не распределять fetch по страницам. Предлагаемые настройки `VITE_DATA_SOURCE=mock|api` и `VITE_API_BASE_URL` пока не реализованы. Не смешивать mock-состояние с серверными сущностями.
3. Добавить выбранный userId и teamId вместо констант. Загрузить users, teams, tags, achievements. Передавать `X-Demo-User-ID` для private reads/mutations; роль капитана получать из members. При смене персоны отменять запросы и таймеры, очищать или разделять private cache.
4. Подключить read-only каталог, карточки, профили. Snake_case переводить в domain-модель в одном адаптере. В UI оставить строки ID; числовые DTO принимать/отправлять только после проверки safe integer. Для больших bigint потребуется изменение сервера или lossless JSON parsing.
5. Переделать создание/уточнения под реальный асинхронный цикл. `POST /tasks` → polling → GET questions → полный answers с revision → polling → редактор → PATCH → polling → confirm revision → publish. Оценки API авторитетны; локальную арифметику к ним не добавлять.
6. Развести private draft/evaluation и подтверждённую public card. PATCH отправляет только изменённые разрешённые поля; пустые строки/массивы сохраняются как намеренная очистка. `202` означает сохранение и очередь работы, а не готовый AI-результат. `409` требует повторного чтения с сохранением несохранённого ввода пользователя.
7. Подключить предложения и milestones после согласования отличий ниже. Создание трёх этапов — несколько запросов, поэтому после таймаута сначала перечитать состояние, а не создавать всё снова. Явно завершать proposal и task по их серверным условиям.
8. После начисляющих операций перечитывать профиль. Серверные user.exp, exp_history и achievements — источник истины. Не использовать локальный ledger как вторую систему начисления. Level можно выводить из EXP; evidence-gated rank требует достоверного состава выполненных личных проектов, которого текущий профиль не предоставляет.

HTTP-клиент должен учитывать прямой object/array response, пустой 204, nullable lists, ошибки `error.code/message`, таймауты и AbortController. Polling: 1→5 секунд, предел 3 минуты; остановка на succeeded/failed, смене revision/персоны и уходе со страницы. Retry — явное действие. Повтор POST после сетевого сбоя может продублировать сущности; сначала перечитать состояние.

## Что согласовать с backend, чтобы сохранить наш MVP

1. Личное подтверждение участников, descriptions/skills и неизменяемый snapshot состава.
2. Дата этапа, критерии приёмки и серверное хранение истории submissions/reviews с комментариями.
3. Политика XP: 200/300/300 каждому подтверждённому участнику либо командный пул. Уточнить дополнительные task rewards и каталог достижений, чтобы награды не суммировались неожиданно.
4. Раздельный выбор/старт, единый проектный snapshot, ограничения последовательности этапов и способ завершения.
5. Достоверный источник completed verified projects для рангов и портфолио — membership, tags и EXP сами по себе недостаточны.

Рекомендация: начать с API-каталога, пользователей и AI-постановки задач; доставку и прогрессию подключать после фиксации правил. Если цель — максимально быстрый серверный demo, можно принять backend-семантику, но явно убрать обещания индивидуальной проверки, сроков и истории, которые контракт пока не сохраняет. Это отдельное изменение согласованного продукта, а не техническая замена mock на fetch.
