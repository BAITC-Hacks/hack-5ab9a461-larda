# ERD Larda: границы frontend и вопросы к backend

Дата: 2026-09-23. Источник: Mermaid ERD, присланная пользователем в чате. Анализ выполнен по схеме, а не по SQL-миграциям: отсутствие ограничения на диаграмме не доказывает его отсутствия в БД. Изменения БД и API здесь не реализованы.

## Что принимаем из ERD

- Владельцем задачи является `USERS.id` через `TASKS.owner_id`. Таблицы организаций нет; прежняя идея `Organization` не является текущим контрактом.
- Роль пользователя — `business | student`. Роль в команде — отдельно `captain | member`. Переключатель демонстрационных пользователей в UI не является авторизацией.
- `publication_status` и `execution_status` — независимые состояния. «Команда выбрана» в UI определяется наличием принятого отклика, а не новым значением `publication_status`.
- Готовность постановки `readiness_score` не равна опыту `USERS.exp` и не должна увеличиваться от наград за выполнение.
- Отклик принадлежит команде; `submitted_by` фиксирует конкретного отправителя, `decided_by` — автора решения бизнеса.
- Этапы выполнения, достижения и опыт предусмотрены ERD, но не входят в текущую пересборку интерфейса создания задачи и выбора команды.

## Замечания по приоритету

### HIGH — полномочия не следуют из обычных FK

FK на `USERS` доказывает существование пользователя, но не его право действовать. На backend нужно проверять: владелец задачи имеет роль бизнеса; отправитель состоит в соответствующей команде и имеет разрешение отправлять отклик; решение принимает владелец задачи. Для MVP рекомендуется разрешать отправку капитану. Право подтверждать этап выполнения также нужно определить отдельно.

Проверка: подмена `owner_id`, `submitted_by`, `decided_by`, чужого `team_id` не позволяет изменить чужие данные. Пользователь действия определяется серверной сессией, а не доверенным полем тела запроса.

### HIGH — количество выбранных команд требует продуктового решения

ERD допускает несколько `accepted` откликов для одной задачи. Формулировка `team_exp_reward` как пула каждой завершившей команды тоже совместима с несколькими исполнителями. Согласованный текущий UI выбирает одну команду.

Рекомендация для этого MVP: подтвердить с backend правило «не больше одного принятого отклика на задачу» и обеспечить его атомарно, например частичным уникальным индексом по `task_id` при `status = 'accepted'`. Остальные отклики остаются `pending`, пока бизнес отдельно не отклонит их. Если продукт выбирает несколько команд, индекс не нужен, но текущий UI и завершение задачи потребуется изменить.

Проверка: два конкурентных принятия не выбирают две команды при политике одного исполнителя.

### HIGH — награды нуждаются в идемпотентности и согласованных источниках

Обычные FK в `EXP_TRANSACTIONS` не запрещают повторное начисление, чужой источник или несовместимые комбинации nullable-полей. `reason` должен определять допустимый источник:

| Причина | Источник | Предлагаемая уникальность начисления |
| --- | --- | --- |
| `milestone_completed` | `milestone_id` | `user_id + milestone_id + reason` |
| `team_task_completed` | `task_id + team_id` | `user_id + task_id + team_id + reason` |
| `business_task_completed` | `task_id` | `user_id + task_id + reason` |
| `achievement_unlocked` | `achievement_id` вместе с получателем | `user_id + achievement_id + reason` |

Нужно проверять связи task/team/proposal у командной награды, а не только существование ID. Начисление и изменение кеша `USERS.exp` должны выполняться одной транзакцией; ledger — источник для сверки суммы. Обычный UNIQUE с nullable-полями не всегда предотвращает дубликаты; предпочтительны отдельные частичные ограничения для причин.

Проверка: повтор события и параллельные запросы создают одно начисление; откат операции не оставляет изменённый баланс.

### HIGH — состав получателей командного пула не зафиксирован

`TEAM_MEMBERS` отражает текущий состав. Он сам по себе не отвечает, кто получает награду, если участник присоединился после выполнения или вышел до начисления. Требуется определить момент фиксации получателей, правило деления и распределения остатка.

Рекомендация: согласовать снимок участников на принятие отклика либо на начало этапа; делить целочисленный пул на зафиксированных получателей, остаток распределять детерминированно. Сумма персональных транзакций должна равняться пулу. Отдельно подтвердить, суммируются ли награды этапов и финальная награда задачи. Это решения backend/product, не реализованные frontend-допущения.

### MEDIUM — составной FK достижения нужно реализовать именно составным

`USER_ACHIEVEMENTS` имеет PK `(user_id, achievement_id)`. Поле `EXP_TRANSACTIONS.achievement_id` не может самостоятельно ссылаться на эту таблицу как на уникальную запись. Комментарий ERD уже подразумевает правильный составной FK: `(user_id, achievement_id) -> USER_ACHIEVEMENTS(user_id, achievement_id)`.

Связь `o|--o|` на диаграмме описывает максимум одну транзакцию на полученное достижение, но сам FK этого не гарантирует: нужна соответствующая уникальность. При nullable `achievement_id` дополнительно требуется согласованность с `reason`.

Проверка: нельзя начислить пользователю бонус за достижение другого пользователя; повторный бонус отклоняется.

### MEDIUM — уникальность командных действий и порядок вопросов

- Подтвердить `UNIQUE(task_id, team_id)` для откликов. Это удобно для MVP с одним предложением команды; если нужны версии или повторная подача после отказа, требуется другая модель.
- Подтвердить максимум одного капитана на команду. Частичный уникальный индекс обеспечивает «не более одного», но наличие хотя бы одного капитана требует логики создания и передачи роли в транзакции.
- Рекомендуется `UNIQUE(task_id, round_number, position)` для вопросов и `UNIQUE(proposal_id, position)` для этапов. Одинаковый `field_key` в разных раундах допустим, когда помощник уточняет прежний ответ.
- Отдельно определить допустимые `field_key` и форму `draft_card`, `score_breakdown`, `interests`: `jsonb` не гарантирует контракт содержимого.

Проверка: двойная отправка формы не создаёт два отклика; смена капитана не оставляет двух капитанов; вопросы возвращаются в стабильном порядке.

### MEDIUM — жизненный цикл и подтверждение карточки не формализованы

Статусы ERD перечислены, но правила переходов отсутствуют. Для текущего UI предлагается:

1. Создание: `publication_status = draft`, `execution_status = not_started`.
2. Помощник формирует кандидаты в `draft_card`; неизвестные факты остаются пустыми. Ответы сохраняются в `TASK_QUESTIONS.answer`.
3. Проверка пользователем переносит подтверждённые поля и `tag_ids` в поля `TASKS`/`TASK_TAGS`, записывает `confirmed_at`.
4. Публикация проверяет подтверждение и требуемую готовность, записывает `published_at`, меняет только статус публикации.
5. Принятие отклика отражается в `PROPOSALS.status`. Автоматический старт выполнения при принятии нужно согласовать; UI не должен выдумывать такой переход.

Порог 70 — правило текущего прототипа, не ограничение из ERD. Нужно согласовать поведение повторного редактирования: когда сбрасывается подтверждение и может ли уже опубликованная карточка измениться. Архивирование публикации не равно отмене исполнения. Завершение задачи и отклика должно иметь проверяемые условия и согласованные даты.

Проверка: нельзя обойти публикационные условия прямым запросом; изменение неподтверждённого черновика не незаметно меняет опубликованные факты.

### MEDIUM — вход в систему находится вне предоставленной схемы

У `USERS` нет email, идентичностей провайдера или иных данных входа. Это не ошибка, если авторизация находится в отдельном сервисе или схеме. До подключения реального backend нужно получить способ связи проверенной сессии с `USERS.id`. Добавлять произвольный `passwordHash` в текущий frontend-контракт не следует.

### LOW — целостность чисел и аудит изменений

Подтвердить CHECK для диапазона готовности `0..100`, положительного `duration_days`, допустимых статусов, положительных позиций и неотрицательных пулов наград. Политика отрицательных ledger-транзакций для коррекций требует отдельного решения. `created_at`/`updated_at` у задач и откликов, версия обновления и правила удаления связанных записей полезны для сортировки и конфликтов, но в ERD не заданы.

## Соответствие frontend-модулей ERD

| Модуль | Источник данных | Ограничение текущего UI |
| --- | --- | --- |
| Демо-контекст пользователя | `USERS`, `TEAM_MEMBERS`, `TEAMS` | Выбор заранее заданного пользователя, без настоящей авторизации |
| Мои задачи | `TASKS.owner_id` | Показывать задачи текущего бизнеса |
| Пошаговое создание | `TASKS`, `TASK_QUESTIONS`, `draft_card` | Массив вопросов; три вопроса — только демонстрационные данные |
| Проверка и публикация | Подтверждённые поля `TASKS`, `TASK_TAGS` | Сохранять введённые пользователем факты |
| Каталог | Опубликованные `TASKS`, `TASK_TAGS`, `TAGS` | Сортировка по готовности, не по опыту |
| Отклик | `PROPOSALS`, `TEAMS`, `TEAM_MEMBERS` | `plan` — текст; команда определяется контекстом капитана |
| Выбор команды | `PROPOSALS.status`, `decided_by`, `decided_at` | Одно принятое предложение по политике текущего UI |
| Выполнение и награды | `MILESTONES`, `ACHIEVEMENTS`, `USER_ACHIEVEMENTS`, `EXP_TRANSACTIONS` | Будущие самостоятельные модули, не текущие экраны |

## Граница будущего API

- Все bigint ID передавать строками: JavaScript `number` не гарантирует точность для полного диапазона bigint. Это относится также к FK и ID внутри JSON.
- Внутренние camelCase-модели UI допустимы; преобразование snake_case DTO выполнять в одном adapter/repository, а не в компонентах.
- Контракт нужен для операций: список/получение задач, создание черновика, получение вопросов, сохранение ответа, подтверждение карточки, публикация, отправка отклика и решение бизнеса. URL, envelope и HTTP-коды из ERD неизвестны; не считать предложенные ранее маршруты утверждённым API.
- До появления API mock repository реализует те же пользовательские операции локально. Компоненты не импортируют fixtures, не делают `fetch` и не работают напрямую с хранилищем браузера.
- `proposalCount`, состав/название команды и статус «Команда выбрана» — проекции связей; не добавлять их как якобы существующие колонки ERD.
- Backend должен вернуть формат ошибок и серверную готовность; арифметика readiness в демонстрации не является окончательной бизнес-формулой.

## Что подтвердить при подключении backend

Одна или несколько команд на задачу; повторные отклики; полномочия капитана; контракт `draft_card` и подтверждения; переходы выполнения; авторизация; форма DTO/ID; идемпотентность наград и состав получателей. Эти решения отмечены как рекомендации, а не как уже реализованные свойства БД.
