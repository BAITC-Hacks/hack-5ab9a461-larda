# Frontend Larda

## Запуск и проверки

Из корня репозитория:

```bash
npm install
npm run dev
```

Vite выводит адрес приложения (обычно http://localhost:5173). Для production:

```bash
npm run build
npm run preview
```

Проверка полного сценария в Chromium:

```bash
npx playwright install chromium
npm run test:e2e
```

Тесты сами поднимают и останавливают сервер на 127.0.0.1:4175, не занимая 5173. Скриншоты сохраняются в `test-results/` и не входят в Git. Сервер размещения сборки должен отдавать `index.html` для frontend-маршрутов (SPA fallback).

## Проверка за несколько минут

1. Выберите «Я представляю бизнес», затем «Создать задачу».
2. Введите название и описание. Сохранение описания даёт 25 баллов.
3. По очереди ответьте, что нужно получить (+20), как оценить результат (+15) и какие данные есть (+15). Ответы становятся карточкой, без вымышленных фактов.
4. Нажмите «Проверить задачу». При необходимости измените детали и опубликуйте. Дополнительные поля дают ещё до 25 баллов.
5. Откройте задачу в каталоге. Кнопка «Перейти к отклику как студент» включает демо-контекст капитана команды «Нова».
6. Отправьте идею, план и срок. Ссылка на прототип необязательна.
7. Через «Сменить роль» вернитесь в бизнес. Откройте свою задачу и «Отклики команд», отметьте команду и подтвердите выбор.

В начальных данных уже есть две опубликованные задачи и два отклика на свою задачу `101`. У новой задачи отклики появляются только после реальной отправки формы. Готовность — локальная оценка полноты полей, не оценка качества текста настоящим AI.

## Маршруты

| Адрес | Экран |
| --- | --- |
| `/` | Выбор роли |
| `/business` | Рабочий стол и следующее действие |
| `/business/tasks` | Мои задачи |
| `/business/tasks?view=responses` | Все мои задачи с откликами |
| `/business/new?task=<id>` | Создание или продолжение черновика |
| `/business/tasks/:id` | Проверка и публикация |
| `/business/tasks/:id/responses` | Ручной выбор команды |
| `/catalog` | Опубликованные задачи |
| `/catalog/:id` | Задача и форма отклика |

URL управляет экраном, данные лежат в `sessionStorage` под ключом `larda.workspace.v1`. Обновление страницы сохраняет подтверждённые действия в этой вкладке. Несохранённый текст формы может потеряться; постоянного серверного хранения и синхронизации устройств нет. Для чистого демо очистите этот ключ в DevTools и обновите страницу.

## Как добавить свой модуль

1. Создайте `src/features/<название>/` с экраном и специфичными компонентами.
2. Общие типы/правила разместите в `src/domain`, повторно используемый UI — в `src/shared`.
3. Добавьте операции в `WorkspaceRepository` и их локальную реализацию в `mockRepository`. Не обращайтесь к хранилищу из страницы.
4. Используйте `useWorkspace()` для чтения snapshot и вызова операций. Методы возвращают Promise, ошибки показываются рядом с действием.
5. Зарегистрируйте маршрут в `src/app/routes.tsx`, при необходимости добавьте ссылку в `AppShell`.
6. Добавьте проверку пользовательского сценария и обновите `contextn.md` / `progress.md`.

Зависимости направлены так: `app → features → shared/domain`; `data → domain`; provider предоставляет репозиторий. Между feature-модулями нет прямых импортов. Общий CSS содержит палитру и базовые элементы; анимации выделены в отдельный модуль с reduced motion.

## Подключение backend после согласования API

`WorkspaceRepository` — контракт frontend, а не утверждённый REST API. Реальный адаптер должен загрузить данные, отдавать стабильный snapshot, уведомлять подписчиков после изменений, преобразовывать DTO в доменные модели и реализовать операции. Для загрузки/сетевых ошибок добавляется состояние инициализации в provider. Точка подключения адаптера — `src/App.tsx`.

Обязательные серверные проверки: владельцы задач, членство/капитан команды, допустимые статусы, повторные отклики и конкурентный выбор команды. Переключатель роли в демо не является авторизацией.

Все ID — строки. Mock использует UUID для новых записей; backend может передавать SQL bigint как строки. Модель интерфейса — используемое подмножество ERD, не её полная копия. `publicationStatus` и `executionStatus` разделены; выбранная команда определяется по accepted-отклику. Readiness отдельно от EXP. Теги пока представлены демонстрационными метками; их связи по ID, навыки пользователей и подбор команды потребуют API.

Подробный разбор и вопросы к backend: [ERD_REVIEW.md](ERD_REVIEW.md). Этапы работ, опыт и достижения остаются будущими модулями.
