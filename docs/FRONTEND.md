# Frontend Larda

## Запуск и проверки

Из корня репозитория:

```bash
npm install
npm run dev
```

Vite выводит адрес приложения (обычно http://localhost:5173). Для production:

```bash
npm run build
npm run preview
```

Проверка полного сценария в Chromium:

```bash
npx playwright install chromium
npm run test:e2e
```

Тесты сами поднимают и останавливают сервер на 127.0.0.1:4175, не занимая 5173. Скриншоты сохраняются в `test-results/` и не входят в Git. Сервер размещения сборки должен отдавать `index.html` для frontend-маршрутов (SPA fallback).

## Проверка за несколько минут

Сквозной сценарий и формула готовы в [README](../README.md). Для короткого показа исполнения: выберите бизнес → отклики задачи «Снижение списаний кофейни» → команда «Нова» → проект. Укажите три критерия и даты; переключайтесь между бизнесом и студентом для отправки, доработки и принятия результатов.

Начальные пять карточек и пять откликов — синтетические. `/student/example` показывает независимый подготовленный профиль без изменения данных. Свежий студент начинает с нулевым XP.

## Маршруты

| Адрес                            | Экран                                      |
| -------------------------------- | ------------------------------------------ |
| `/`                              | Выбор роли                                 |
| `/business`                      | Рабочий стол и следующее действие          |
| `/business/tasks`                | Мои задачи                                 |
| `/business/tasks?view=responses` | Все мои задачи с откликами                 |
| `/business/new?task=<id>`        | Создание или продолжение черновика         |
| `/business/tasks/:id`            | Проверка и публикация                      |
| `/business/tasks/:id/responses`  | Ручной выбор команды                       |
| `/catalog`                       | Опубликованные задачи                      |
| `/catalog/:id`                   | Задача и форма отклика                     |
| `/student`                       | Прогресс студента                          |
| `/student/catalog`               | Каталог задач для студента                 |
| `/student/catalog/:id`           | Условия задачи и отправка предложения      |
| `/student/example`               | Синтетический профиль только для просмотра |
| `/student/projects/:proposalId`  | Результаты и история миссии                |
| `/business/projects/:proposalId` | Настройка и проверка проекта               |

URL управляет экраном, данные лежат в `sessionStorage` под ключом `larda.workspace.v2`. Обновление страницы сохраняет подтверждённые действия в этой вкладке. Несохранённый текст формы может потеряться; постоянного серверного хранения и синхронизации устройств нет. Для чистого демо очистите оба ключа `larda.workspace.v1` и `larda.workspace.v2` в DevTools и обновите страницу. Миграция оставляет исходный v1 для восстановления.

## Как добавить свой модуль

1. Создайте `src/features/<название>/` с экраном и специфичными компонентами.
2. Общие типы/правила разместите в `src/domain`, повторно используемый UI — в `src/shared`.
3. Добавьте операции в `WorkspaceRepository` и их локальную реализацию в `mockRepository`. Не обращайтесь к хранилищу из страницы.
4. Используйте `useWorkspace()` для чтения snapshot и вызова операций. Методы возвращают Promise, ошибки показываются рядом с действием.
5. Зарегистрируйте маршрут в `src/app/routes.tsx`, при необходимости добавьте ссылку в `AppShell`.
6. Добавьте проверку пользовательского сценария и обновите `contextn.md` / `progress.md`.

Зависимости направлены так: `app → features → shared/domain`; `data → domain`; provider предоставляет репозиторий. Feature-компоненты могут использовать соседние компоненты своего модуля; общие примитивы остаются в shared. Общий CSS содержит палитру и базовые элементы; анимации выделены в отдельный модуль с reduced motion.

## Подключение backend после согласования API

`WorkspaceRepository` — контракт frontend, а не утверждённый REST API. Реальный адаптер должен загрузить данные, отдавать стабильный snapshot, уведомлять подписчиков после изменений, преобразовывать DTO в доменные модели и реализовать операции. Для загрузки/сетевых ошибок добавляется состояние инициализации в provider. Точка подключения адаптера — `src/App.tsx`.

Обязательные серверные проверки: владельцы задач, членство/капитан команды, допустимые статусы, повторные отклики и конкурентный выбор команды. Переключатель роли в демо не является авторизацией.

Все ID — строки. Mock использует UUID для новых записей; backend может передавать SQL bigint как строки. Модель интерфейса — используемое подмножество ERD, не её полная копия. `publicationStatus` и `executionStatus` разделены; выбранная команда определяется по accepted-отклику. Readiness отдельно от EXP. Навыки — строковые метки задачи и доказательства принятого личного вклада; связи по ID и подбор команды потребуют API.

Подробный разбор и вопросы к backend: [ERD_REVIEW.md](ERD_REVIEW.md). Локальные этапы, опыт и достижения описаны в [GAMIFICATION.md](GAMIFICATION.md); серверная реализация остаётся будущей.
