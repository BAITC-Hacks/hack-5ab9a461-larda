# Контекст Larda

## Текущий продукт

Larda — MVP на React, TypeScript, Vite, Go и PostgreSQL. Бизнес формулирует задачи и контролирует поставку; студенты получают XP за подтверждённый вклад. Основной интерфейс обращается к Go API через same-origin `/api`; задачи и прогресс сохраняются в PostgreSQL. Старый локальный интерфейс доступен через `VITE_DATA_MODE=local`. Доступ выбирается demo-header без авторизации. Сквозной запуск проверен с серверным AI fallback; отдельно через Docker проверены реальные OpenAI-задания вопросов и генерации карточки (source=openai). Начальные пять задач и пять откликов синтетические. Новые формы сохраняют реальные введённые данные.

Основной серверный сценарий: описание → 3–7 вопросов → все ответы → оценённая карточка → ручное подтверждение и публикация → заявка капитана → выбор команды → согласованные этапы → результат / доработка / принятие → явное завершение команды и задачи → серверный XP и достижения.

## Основной интегрированный режим (актуальное состояние)

`App` по умолчанию открывает серверный кабинет с автоматической загрузкой пользователей и команд. API base — текущий origin; Vite проксирует `/api` и `/healthz` на `API_PROXY_TARGET` (по умолчанию 127.0.0.1:8080). Docker Compose добавляет web/nginx, который отдаёт dist и проксирует API; браузеру достаточно порта 3000. `VITE_API_BASE_URL` — необязательный явно заданный удалённый API. Секретов модели в Vite env нет. Compose вычисляет WEB_ORIGINS из WEB_PORT (localhost и 127.0.0.1) и добавляет оба dev-origin 5173; backend объединяет их с CORS_ORIGINS без wildcard. Это предотвращает 403 при смене порта и при старом явном списке CORS. Проверка origin не отключается. Frontend healthcheck проверяет HTML и API через nginx; для применения нового кода/окружения нужен up --build с пересозданием контейнеров.

Профиль, раздел и задача сохраняются в query `user`/`view`/`task`; refresh и браузерная история восстанавливают серверные записи. Членство команд обновляется при загрузке. API-запросы отменяются при смене профиля/задачи; приватные данные разделены. Подтверждение карточки сбрасывается при смене revision.

В общей светлой оболочке бизнес видит отдельные разделы «Рабочий стол», «Мои задачи», «Отклики и проекты»; студент — «Каталог задач», «Мои проекты», «Мой прогресс». Каталог не смешан с формами и достижениями. Подготовка задачи: описание → уточнения по одному → карточка → публикация. Заявка: идея → план → проверка/отправка. Кнопка «Назад» сохраняет ввод между шагами; закрытие формы заявки внутри задачи сохраняет черновик до ухода со страницы. Refresh или переход в другой раздел не сохраняет несохранённый текст. Студент видит уровень по серверному XP, серверные достижения, ссылки на принятые результаты и объявленные навыки. Каталог допускает поиск и фильтры открытых задач, черновиков и готовности от 70%. Статусы и причины XP переводятся для интерфейса. Все мутации сохраняет backend; UI не начисляет XP.

Серверные правила отличаются от локальной RPG-модели выше: допускаются несколько команд; принятие заявки начинает работу; число этапов произвольное, XP делится между текущими участниками; достижения определяет backend; завершение команды и задачи явное. Ранг и индивидуальная атрибуция навыков из локальной модели не выдаются за серверную верификацию. Лимит каталога/списка своих задач пока 100 записей; нет production-auth, загрузки файлов и формы управления командами.

Автоматический полный сценарий использует отдельную проверочную БД и API с `AI_MODE=fallback`. Реальный OpenAI отдельно проверен через Docker frontend: вопросы и карточка успешно сгенерированы, source=openai. `GET /api/v1/runtime` показывает только настроенный режим, а источник конкретной сохранённой оценки остаётся в задаче; старое значение fallback не означает текущий режим API. Рендер, переход назад и polling не создают AI-заданий. Ошибка чтения после успешной мутации не превращает сохранённое действие в неуспех и не запускает повторную отправку. Исторические записи об отсутствии API относятся к предыдущим этапам. Запуск: `docs/RUN_INTEGRATED.md`.

## Правила сохранённого локального демо (`VITE_DATA_MODE=local`)

- Разделены readiness, publicationStatus, executionStatus, project progress и student XP. Выбор команды не запускает исполнение автоматически и не отклоняет остальные отклики.
- Readiness оценивает полноту: контекст/потребность 10+10, данные 20, результат 15, критерии 15, ограничения 10, пользователи 10, контакт/взаимодействие 5+5. Обратная связь хранится без дополнительных баллов.
- Порога публикации 70 больше нет. Нужны название, контекст, подтверждение. Неопубликованные черновики приватны; любые опубликованные задачи доступны в каталоге и открыты для отклика до выбора команды. Ранг доступа не ограничивает.
- Бизнес может подтвердить правки опубликованной задачи до старта. Старт фиксирует brief, навыки и участников.
- Три последовательных этапа: анализ 200 XP, прототип 300, итог 300. Критерии и сроки вводит бизнес. Капитан отправляет доказательства и вклад каждого участника. Бизнес подтверждает конкретных участников или запрашивает изменения. История версий сохраняется.
- Ранг E–S требует одновременно XP и завершённые проекты; уровень L требует `50*L*(L-1)` XP. Три достижения: 1 проект (+100), 5 проектов (+300), 3 бизнес-аккаунта (+200). Опыт вычисляется из ledger.
- Подтверждённый проект требует завершения и хотя бы одного принятого личного вклада. Навыки — ссылки на вклад, без численных уровней. Проверка бизнеса в демо не подтверждает юридическую идентичность.
- Принятие и награды атомарны на уровне snapshot; повтор решения не даёт XP. Прогресс проекта: 0/33/67/100% принятых этапов.

## Архитектура локального демо

`app` подключает маршруты и WorkspaceProvider; `features` читают domain и shared UI; `data` реализует WorkspaceRepository; `domain` не зависит от React/DOM/storage. Страницы не читают sessionStorage и не импортируют fixtures. Read-only пример профиля выдаёт отдельный метод repository.

Владелец задачи — пользователь через ownerId; организаций не добавлено. ID — строки; UUID mock не является согласованным SQL/API-контрактом. Project id связывает agreement с accepted proposal. Новые структуры frontend — не утверждённые endpoints.

`sessionStorage`: `larda.workspace.v2`. Миграция v1 сохраняет тексты и отклики, добавляет пустые новые поля, пересчитывает готовность, не выдумывает XP и сохраняет исходный ключ. Ошибка записи не уведомляет UI о частичном успехе. Закрытие сессии может удалить данные; синхронизации устройств нет. Несохранённые формы могут теряться при навигации.

## Интерфейс сохранённого локального демо

Бизнес: светлая палитра, синий #0B4F7C, зелёный #167A55, крупные действия. Очередь: проверка результата → просрочка → отклики → подготовка → работа → завершение. Метрики берутся из принятых этапов.

Обе роли используют общую светлую палитру, поверхности, типографику и кнопки. Студенческий профиль сохраняет ранги, XP, достижения и доказательства навыков. В шапке явно указан «Каталог задач», в профиле есть заметная кнопка открытия каталога. Анимации используют общий motion и reduced motion.

Маршруты: существующие business/catalog плюс `/student`, `/student/catalog`, `/student/catalog/:id`, `/student/example`, `/student/projects/:proposalId`, `/business/projects/:proposalId`. Прямые ссылки требуют SPA fallback. Выбор роли — демо-контекст.

Помощник детерминированный, с валидатором формата и fallback; не добавляет факты и не выдаётся за подключённую модель.

[Запуск и маршруты](docs/FRONTEND.md), [правила и контракт заглушки](docs/GAMIFICATION.md), [фактические проверки](progress.md).

Для локального демо внешний API не используется. В обоих режимах не реализованы: авторизация, отмена и переоткрытие проектов, отзыв наград, collaboration score, подтверждение компаний, completion rate, численные skill levels, чат и файлы.

## История: первоначальный анализ backend

В `docs/from backend` пользователь добавил frontend guide, JSON reference и Postman-файлы. Они описывают серверный API, но исходников/Compose/OpenAPI в текущем checkout нет, `localhost:8080/healthz` при проверке 2026-09-23 недоступен. Это документированный контракт, не проверенный живой backend.

Правила отличаются от локального MVP: принятие отклика сразу начинает исполнение, допускаются несколько команд/откликов, EXP делится между текущими участниками; submit принимает только URL, review только boolean. Сроков этапов, комментариев, индивидуальных подтверждений и истории версий в присланном контракте нет. Завершение proposal/task отдельное. Не заменять эти различия молча в HTTP-адаптере.

Разбор и порядок подключения: [BACKEND_INTEGRATION.md](docs/BACKEND_INTEGRATION.md). Добавлен отдельный серверный кабинет `/connected`; текущие локальные правила выше остаются действующими в основном MVP. Живой API пока недоступен.

Повторная проверка backend: `for_frontend (2).md` описывает ручную Postman-папку 03, но сохранённая collection содержит только папки 01 и 02. Файл collection (2) на диске не обнаружен. Условия геймификации в доступном контракте не изменились.

## История: первый отдельный серверный кабинет

`/connected` открывается с экрана выбора роли. Пользователь вводит URL backend; клиент загружает пользователей и команды, отправляет `X-Demo-User-ID` выбранной персоны. HTTP вынесен в `src/data/backendClient.ts`, серверный UI — в `src/features/connected`. Это отдельный компактный сценарий, не HTTP-замена локального WorkspaceRepository.

Поддержаны: создание задачи, опрос AI (до 3 минут), все ответы одним запросом, редактирование изменённых полей, подтверждение revision и публикация; заявки капитана, решение владельца, этапы, сдача ссылки, принятие/доработка, явное завершение команды и задачи; EXP только из серверного профиля. Запросы отменяются при смене персоны; приватные данные сбрасываются. Автоматических повторов мутаций нет. Ошибка связи не включает локальную имитацию.

Ограничения: каталог до 100 задач; соединение/выбор карточки не сохраняются после refresh (серверные данные сохраняет backend); команды обновляются при переподключении; ранги/индивидуальное подтверждение вклада локального MVP не переносятся в серверный режим. Доступность AI определяется backend, `fallback` не является внешней моделью. Для показа нужен URL живого backend и разрешённый CORS origin.
