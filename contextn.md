# Контекст Larda

## Текущий продукт

Larda — frontend MVP на React, TypeScript, Vite. Бизнес формулирует задачи и контролирует поставку; студенты получают XP за подтверждённый вклад. Backend, авторизация и внешний AI отсутствуют. Начальные пять задач и пять откликов синтетические. Новые формы сохраняют реальные введённые данные.

Основной сценарий: описание → минимум три предлагаемых уточнения → редактируемая карточка → ручное подтверждение и публикация → отклик → ручной выбор одной команды → настройка и старт трёх этапов → результат / доработка / принятие → опыт и достижения.

## Устойчивые решения

- Разделены readiness, publicationStatus, executionStatus, project progress и student XP. Выбор команды не запускает исполнение автоматически и не отклоняет остальные отклики.
- Readiness оценивает полноту: контекст/потребность 10+10, данные 20, результат 15, критерии 15, ограничения 10, пользователи 10, контакт/взаимодействие 5+5. Обратная связь хранится без дополнительных баллов.
- Порога публикации 70 больше нет. Нужны название, контекст, подтверждение. Неопубликованные черновики приватны; любые опубликованные задачи доступны в каталоге и открыты для отклика до выбора команды. Ранг доступа не ограничивает.
- Бизнес может подтвердить правки опубликованной задачи до старта. Старт фиксирует brief, навыки и участников.
- Три последовательных этапа: анализ 200 XP, прототип 300, итог 300. Критерии и сроки вводит бизнес. Капитан отправляет доказательства и вклад каждого участника. Бизнес подтверждает конкретных участников или запрашивает изменения. История версий сохраняется.
- Ранг E–S требует одновременно XP и завершённые проекты; уровень L требует `50*L*(L-1)` XP. Три достижения: 1 проект (+100), 5 проектов (+300), 3 бизнес-аккаунта (+200). Опыт вычисляется из ledger.
- Подтверждённый проект требует завершения и хотя бы одного принятого личного вклада. Навыки — ссылки на вклад, без численных уровней. Проверка бизнеса в демо не подтверждает юридическую идентичность.
- Принятие и награды атомарны на уровне snapshot; повтор решения не даёт XP. Прогресс проекта: 0/33/67/100% принятых этапов.

## Архитектура

`app` подключает маршруты и WorkspaceProvider; `features` читают domain и shared UI; `data` реализует WorkspaceRepository; `domain` не зависит от React/DOM/storage. Страницы не читают sessionStorage и не импортируют fixtures. Read-only пример профиля выдаёт отдельный метод repository.

Владелец задачи — пользователь через ownerId; организаций не добавлено. ID — строки; UUID mock не является согласованным SQL/API-контрактом. Project id связывает agreement с accepted proposal. Новые структуры frontend — не утверждённые endpoints.

`sessionStorage`: `larda.workspace.v2`. Миграция v1 сохраняет тексты и отклики, добавляет пустые новые поля, пересчитывает готовность, не выдумывает XP и сохраняет исходный ключ. Ошибка записи не уведомляет UI о частичном успехе. Закрытие сессии может удалить данные; синхронизации устройств нет. Несохранённые формы могут теряться при навигации.

## Интерфейс

Бизнес: светлая палитра, синий #0B4F7C, зелёный #167A55, крупные действия. Очередь: проверка результата → просрочка → отклики → подготовка → работа → завершение. Метрики берутся из принятых этапов.

Обе роли используют общую светлую палитру, поверхности, типографику и кнопки. Студенческий профиль сохраняет ранги, XP, достижения и доказательства навыков. В шапке явно указан «Каталог задач», в профиле есть заметная кнопка открытия каталога. Анимации используют общий motion и reduced motion.

Маршруты: существующие business/catalog плюс `/student`, `/student/catalog`, `/student/catalog/:id`, `/student/example`, `/student/projects/:proposalId`, `/business/projects/:proposalId`. Прямые ссылки требуют SPA fallback. Выбор роли — демо-контекст.

Помощник детерминированный, с валидатором формата и fallback; не добавляет факты и не выдаётся за подключённую модель.

[Запуск и маршруты](docs/FRONTEND.md), [правила и контракт заглушки](docs/GAMIFICATION.md), [фактические проверки](progress.md).

Не реализованы: backend, реальный AI, авторизация, отмена и переоткрытие проектов, отзыв наград, collaboration score, подтверждение компаний, completion rate, численные skill levels, чат и файлы.

## Полученный контракт backend

В `docs/from backend` пользователь добавил frontend guide, JSON reference и Postman-файлы. Они описывают серверный API, но исходников/Compose/OpenAPI в текущем checkout нет, `localhost:8080/healthz` при проверке 2026-09-23 недоступен. Это документированный контракт, не проверенный живой backend.

Правила отличаются от локального MVP: принятие отклика сразу начинает исполнение, допускаются несколько команд/откликов, EXP делится между текущими участниками; submit принимает только URL, review только boolean. Сроков этапов, комментариев, индивидуальных подтверждений и истории версий в присланном контракте нет. Завершение proposal/task отдельное. Не заменять эти различия молча в HTTP-адаптере.

Разбор и порядок подключения: [BACKEND_INTEGRATION.md](docs/BACKEND_INTEGRATION.md). Интеграция API пока не выполнена; текущие локальные правила выше остаются действующими.

Повторная проверка backend: `for_frontend (2).md` описывает ручную Postman-папку 03, но сохранённая collection содержит только папки 01 и 02. Файл collection (2) на диске не обнаружен. Условия геймификации в доступном контракте не изменились.
